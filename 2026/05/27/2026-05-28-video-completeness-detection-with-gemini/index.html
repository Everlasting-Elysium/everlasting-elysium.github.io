用 Gemini 多帧理解做视频完整性检测：两步采样的思路

2026 / 05 / 28
计算机视觉 Gemini 视频理解 多模态 Prompt Engineering

项目里有一条质量规则：第一人称拍摄的视频，录制必须完整——开头不能是动作已经在进行中（开晚了），结尾不能卡在动作半截（关早了）。

听起来不难，但一展开就有意思了。”完整”这个概念带语义——你得知道这个任务是什么、包含几个步骤、从什么状态开始算起、到什么状态算结束。纯靠传统视觉做不了这件事。

今天的实验：拿 Gemini 的多帧理解能力来判断。记录一下思路和踩的坑。

为什么不能直接把视频丢给模型

最直觉的想法是把整段视频传给 Gemini，问它”这视频完整吗”。

不行，两个原因：

  1. Token 成本。一段 3 分钟的视频按 1fps 抽帧就是 180 张图，每张图按 768px 算，token 开销巨大。实际场景要跑几百上千条视频，成本不可接受。
  2. 注意力稀释。帧数越多，模型对每一帧的注意力越分散。而完整性判断的关键信息集中在开头和结尾——中间大段都是正常执行过程，对判定没什么帮助。

所以核心问题变成了：怎么用尽可能少的帧，覆盖到最关键的信息。

两步走：先规划，再判断

最终方案是两步 LLM 调用。

Step 1：任务周期估算。 把任务描述发给 Gemini（纯文本，没有图），让它估算执行一次这个任务需要多长时间、分几步。比如”在厨房洗碗并放到碗柜”，模型会拆成打开水龙头→挤洗洁精→刷碗→冲洗→放碗柜，估算总共 2 分钟。

Step 2：智能采样 + 完整性判断。 根据估算出的周期时长和步骤边界，生成一个采样计划，然后从视频里抽帧、发给 Gemini 做多帧理解。

这样一来，10-20 帧就能覆盖一段几分钟甚至十几分钟的视频。

采样策略：头尾重、中间轻

完整性检测和普通的视频理解不一样——判定全靠头和尾。所以采样策略是非均匀的：

  • 头部密采：视频前 30% 分配 5 个采样点，用来判断录制开头是否截断
  • 中间按步骤边界采：每个步骤的中点各一帧，确认任务在正常推进
  • 尾部密采：视频后 30% 分配 5 个采样点，用来判断录制结尾是否截断
  • 强制首尾帧：第 0 帧和最后一帧必采

对于可能包含多次重复执行的长视频（比如连续洗了三个碗），会根据 Step 1 估算的周期时长推算循环数，每个循环内都按上述策略铺采样点。

但有个帧预算上限——每个循环至少需要 步骤数 + 2 帧，如果帧预算不够就减少循环数。宁可把少数几个循环看清楚，也不要每个循环都只抽一两帧。

Prompt 的关键区分：”录制完整”≠”任务完美”

Prompt 设计上花了不少心思。最大的坑是：模型很容易把”录制是否被截断”和”任务是否做得好”搞混。

比如一段视频里连续洗了三个碗，第三个碗的步骤比较潦草。模型可能会判”不完整”，但实际上录制本身是完整的——开头有准备动作，结尾有收尾动作，只是后面几次执行质量差了点而已。

所以 prompt 里明确区分了：

“Recording completeness” = Did the camera start BEFORE the task began and stop AFTER the task ended?
This is NOT about whether every repetition of the task is performed perfectly.

并且给了具体的判定标准：

  • COMPLETE：开头能看到任务开始前或刚开始的状态，结尾能看到任务结束或自然停止的状态
  • TRUNCATED：第一帧就已经在做了（开头截断），或最后一帧动作还没做完就断了（结尾截断）

还专门列了”不算截断”的情况：

  • 重复执行时后面几次步骤被压缩了
  • 步骤执行很快、采样帧没抓到
  • 两次执行之间有暂停或无关动作

这些 negative case 的明确列举很重要，不加的话模型误判率会高不少。

输出结构

让模型返回结构化 JSON，方便下游处理：

start/end 各有 evidence 字段，要求模型说出开头和结尾几帧看到了什么。这是个有效的”强制推理”手段——要求模型先描述观察到的内容，再给出判定，能减少胡说的概率。

几个实现细节

帧压缩。采样出来的帧会缩放到最大边 768px，JPEG 质量 85。对于完整性判断来说，分辨率不需要太高，手和物体的粗粒度动作变化就够了。

COS 集成。支持直接从腾讯云 COS 下载视频，本地有缓存机制，同一个视频不会重复下载。方便跑批量实验。

默认回退。如果 Step 1 的周期估算失败（JSON 解析错误、预估时长为 0 之类的），会回退到一个固定策略：头部 20%、尾部 50%、中间 30%。因为即使没有 LLM 规划，头尾密采这个大方向不变。

目前的感受

这个方案的核心优势是成本可控。用两次 API 调用（一次纯文本、一次多帧）替代整段视频的理解，帧数压到 10-20 帧级别，单条视频的成本很低。

但有几个还没解决的问题：

  1. 精度还没系统评估。目前只在两段视频上定性验证了，还没标注 ground truth 做定量 benchmark。后面需要标一批数据跑准确率/召回率。
  2. Step 1 的估算偏差。LLM 对任务时长的估算不一定准，如果严重偏离实际，采样点就会错位。目前的应对是默认回退策略，但更好的做法可能是结合视频的运动特征做自适应采样。
  3. 边缘 case。比如任务描述本身就很模糊（”整理房间”——怎么算整理完了？），或者视频里做了一半换了个完全不同的事。这些情况下模型的判定可信度会打折扣。

下一步打算标注一批数据做正式评估，也准备试试视频开头结尾各截 5 秒直接传视频片段（而非抽帧）的方案，看看对截断检测是否有提升。
